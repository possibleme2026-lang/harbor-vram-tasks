# 推理优化任务族设计

目标：把「8GB 笔记本上做视频扩散推理优化」这件事里**可移植、可判定**的部分，
拆成一批 terminal-bench 任务。每条都给出：难点在哪、verifier 量什么、显存闸门怎么用、
以及**为什么这条能过 sm_90/sm_120 的可移植性检验**。

---

## 0. 一条决定性的筛选规则

先定一条规则，否则做出来的任务会被架构差异毁掉：

> **可移植的优化**：改的是「**做了什么**」——有没有用到融合 kernel、有没有 materialize
> 中间量、切分策略、精度选择、调度顺序。
> **不可移植的优化**：改的是「**在某个 SM 代际上跑得多快**」——Triton autotune 的 config、
> `sm_120` 专属指令、Windows 特有的路径 bug。

H100 是 sm_90，你的卡是 sm_120。前者在任何机器上语义不变，后者换个卡就换答案。
**任务族只收前者。**

这条规则会砍掉一批看起来很诱人的想法，见 §3 的「死路登记」。

---

## 1. 闸门的三档用法

`docs/VRAM_GATE_DESIGN_CN.md` 里的闸门在本任务族里有三种用法，按任务需要选：

| 档位 | 判据 | 适用 |
|---|---|---|
| **A. 显存上限** | 峰值 ≤ 预算 | 「能不能装下」是核心难点 |
| **B. 显存上限 + 下限** | 预算下限 ≤ 峰值 ≤ 预算上限 | 防止「无脑 offload 到 CPU」把显存压到 0 却慢十倍 |
| **C. 三约束** | 显存 + 墙钟时间 + 保真度 | 最接近真实工程，也最难 |

**B 档是个反直觉但必要的设计**：只给上限，最省事的解法是把一切 offload 到 CPU，
显存 0.3 GiB 轻松达标。加下限（比如「峰值 ≥ 4 GiB」）就强制 agent 真的用 GPU，
同时用时间预算挡住纯 offload。这正是真实 8GB 场景下的约束形状。

## 2. 任务清单

> **命名规则（硬约束）**：`scripts/checks/check-task-slug.sh` 要求任务目录名最多
> **3 个连字符分隔的词**（`MAX_TOKENS=3`），且 `[task] name` 必须等于
> `terminal-bench/<目录名>`。T1 最初叫 `wan-dit-vram-budget`（4 词）就是被这条拦下的。
> 下面所有 slug 都已按 3 词校准；新增任务时先数词再动手。

### T1 `wan-vram-budget` ✅ 已实现

- **难点**：两处独立的显存黑洞（二次方注意力矩阵、整卷 fp32 上采样），**只修一处不够**
  （已实测：只修注意力仍 OOM 在 10.35 GiB）。两处都读起来像正常 PyTorch 代码。
- **量什么**：峰值显存（A 档）+ 输出保真度 + 规模未缩水。
- **为什么可移植**：只考核「峰值 ≤ 8GiB」与数值正确性，不涉及 kernel 速度。

### T2 `attention-silent-fallback` ⭐ 最贴近你的真实发现

- **场景**：给一份 SDPA 后端分发器，它按 `set_priority` 排列后端白名单。torch 把
  `set_priority_order` 改名成 `set_priority`，分发器抛 `TypeError` 被**宽泛的 `except`
  吞掉**，白名单静默塌缩成 `[FLASH, MATH]`，实际跑了 11.3× 慢的路径，**没有任何日志**。
- **难点**：agent 看不到任何报错。必须自己**主动探测运行时事实**
  （`torch.backends.cuda.can_use_flash_attention(SDPAParams)`，而不是「没抛异常就算成功」），
  才能发现「可用的更优实现没被用上」。
- **量什么**：C 档——峰值显存 + 墙钟时间 + 数值等价（与参考实现在容差内一致）。
- **为什么可移植**：考的是**分发逻辑正确性**和「有没有主动验证运行时能力」，
  不是 kernel 的绝对性能。时间预算设成粗粒度（比如 ≤ 参考实现 1.5×），
  跨 SM 代际仍然成立。**这是把「静默降级」分类学变成可判定任务的最佳载体。**
- **可加料**：把 `SLA/core.py` 里那个「检测了却没用」的 `arch` 变量、
  以及硬编码的算力表（SM103 vs 真实 SM120）也放进去，让 agent 面对**四种不同的静默降级**，
  其中只有一部分影响最终结果——判断「哪个才是真问题」本身就是难点。

### T3 `int8-gemm-inplace-requant`

- **场景**：`patches/int8_rowwise.py` 那类逐行 int8 GEMM 重量化。
- **难点**：原地 requant 省显存但会踩到 GEMM 的原地别名（cuBLAS 不允许输出与输入重叠）；
  必须找到安全的切分点。同时精度不能掉。
- **量什么**：C 档——显存 + 延迟 + 与 fp32 参考的最大相对误差 ≤ 阈值。
- **可移植性**：⚠️ 需要小心。cuBLAS 的别名规则跨架构一致，但如果 agent 走
  「换一个更快的内核」，答案就不可移植了。**建议只考核「原地 vs 非原地」这一层语义。**

### T4 `streaming-superres-1080p`

- **场景**：流式真超分，1080p 目标只比 2× 多 3% 时间。
- **难点**：既要切分显存，又要保证**帧间时间一致性**（逐帧独立处理后接缝会闪），
  还要保持音频/时间轴对齐。
- **量什么**：显存上限 + 输出帧与参考的 PSNR + **接缝处相邻帧差分的上界**。
  最后这条是本任务独有的——它把「切分」从纯显存问题变成有质量后果的问题。
- **可移植性**：好。一致性约束与硬件无关。

### T5 `kv-cache-budget`

- **场景**：小模型（Qwen2.5-0.5B 级）在线服务，KV cache 必须在预算内，
  同时满足并发数与首 token 延迟下限。
- **难点**：三个量互相拉扯——batch 变大吞吐上去了显存爆了，KV 量化省显存但掉质量。
  必须真的去量 Pareto 前沿，而不是猜。
- **量什么**：C 档 + 最小并发数。
- **可移植性**：好（考的是调度与显存管理，不是 kernel 速度）。

### T6 `triton-cold-cache`

- **场景**：Triton 第一次编译 kernel 会触发 `FileCacheManager` 建目录。
  Windows 上这条路有 bug（你的 `patches/` 里修过），表现为首次调用直接失败。
- **难点**：热身之后一切正常，所以**只有冷启动才复现**。agent 必须意识到要清空缓存重测。
- **量什么**：清空 `~/.triton/cache` 后，首次调用的**延迟上界**与成功性。
- **可移植性**：⚠️ 半好。考「冷启动正确性」可移植，考「Windows 路径 bug」不可移植
  （Linux 容器里根本没这个 bug）。**替代做法**：把场景改成
  「冷启动 + 并发首次调用竞争建缓存目录」，这就是通用的 TOCTOU 问题，跨平台成立。

### T7 `quantization-quality-budget`（PTQ）

- **场景**：给定一个扩散模型，做训练后量化，必须在显存预算内且质量不低于下限。
- **难点**：显存、延迟、质量三者不可兼得，agent 需要在配置空间里搜索并**自我验证**。
- **量什么**：显存 + 质量下限（PSNR/LPIPS）+ 延迟上界。
- **可移植性**：好。但**必须先实验标定阈值**——见 §4。

## 3. 死路登记（明确不做，以及为什么）

| 想法 | 为什么不行 |
|---|---|
| 「优化 Triton kernel 让它在这个 SM 上更快」 | 绝对性能强绑架构。在 H100 上调出的 config 在你的卡上可能更慢，任务没有确定答案 |
| 「修 Windows 上的路径/编码 bug」 | 判据依赖宿主平台；harbor 跑在 Linux 容器里，bug 不复现 |
| 「装好 CUDA 工具链并编译」 | 环境构造问题，不是工程问题；CONTRIBUTING 明确说禁用网络/环境手段制造难度 |
| 「让 14B 模型在 8GB 上跑」（E8 那个） | 需要 2 张卡或超大存储，超出 `gpus = 0|1` 的上限 |
| 「比某个具体版本的 torch 更快」 | 版本一变答案就变，任务会腐烂 |
| 「跑得更快」但不给保真度约束 | agent 可以用降低质量换速度，判据消失（这就是为什么 T2/T3 都带保真度和时间上限） |

## 4. 标定流程（每个任务都必须走一遍）

CONTRIBUTING 对难度的要求是「well beyond the current frontier」，
同时明确反对「靠堆复杂度制造难度」。所以每个任务都要标定三件事：

1. **参考解真的能过**：`harbor run -p tasks/x --agent oracle` 必须拿 1.0。
   本机可以在**真实 8GB 卡**上用 `-e docker` 跑，约束是真的，不需要 Modal。
2. **未改动真的不能过**：`harbor run -p tasks/x --agent nop` 必须拿 0.0。
   **这一步最容易被跳过，也最容易暴露设计缺陷**——T1 就是这么发现
   「峰值测试是空洞的」（见 `VRAM_GATE_DESIGN_CN.md` §7）。
3. **保真度阈值要实验标定**：跑 oracle 与「合法但实现不同」的版本，
   量出真实的数值偏差分布，再把阈值定在它之上、近似解之下。
   T1 实测 oracle 与起始版本在小规模下 `max|diff| = 0`，所以 40 dB 余量很足；
   **一旦任务允许 fp8/int8，这个阈值必须重新标定，不能沿用。**

## 5. 建议的推进顺序

1. **T2 先做**。它是你独有的东西（静默降级分类学），最不可能和别人撞车，
   而且 C 档闸门的全部零件 T1 已经写好了，直接复用。
2. **T1 补 CI**：把三臂（oracle / nop / cheat）做成一个脚本，每次改动后跑一遍。
3. 再按 T5 → T4 → T7 扩展，这三个的 verifier 都是 T1 零件加各自的量。
4. T3/T6 最后做，因为它们的可移植性需要额外论证。

## 6. 与现有任务的差异化

仓库里已有的 GPU 任务：`jax-speedrun-gpu`（训练 recipe，比 loss 和墙钟）、
`fp8-rmsnorm-gemm`（写 CUDA kernel）、`sglang-qwen-burst`（**gpus = 0**，纯服务逻辑）。

**缺口**：现有任务里**没有一个以「显存预算」为核心判据**。
`jax-speedrun-gpu` 有 H100 但不考显存；`fp8-rmsnorm-gemm` 考 kernel 性能但不考显存约束；
`sglang-qwen-burst` 干脆不用 GPU。而 CONTRIBUTING 里点名的方向是
「GPU kernels」和「LLM inference optimization - tuning serving for latency and throughput」，
**都围绕吞吐/延迟，没有围绕显存上限的**。

这正是最值得占的位置：**「让它在这么小的卡上跑得起来」是消费级/边缘部署最真实的约束**，
也是从 GPT-3 时代以来算力叙事里被吞吐指标盖过去的那一半。
